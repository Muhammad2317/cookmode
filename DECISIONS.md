# Decisions log

One line per non-trivial decision: what, why, alternatives considered.

## Phase 0 — Setup

- **Package manager: npm** — already present (v11.6.2), zero extra install, matches Cloudflare Pages default build detection. Alternatives: pnpm/yarn (faster/stricter, but extra install step with no benefit for a solo portfolio project).
- **Next.js scaffold via `create-next-app`** — official, fast path to App Router + TypeScript + Tailwind + ESLint pre-wired correctly for `output: 'export'`. Alternative: hand-roll config — more control but more chance of subtly wrong static-export settings.
- **Vitest for unit tests** — fast, native ESM/TS support, no config ceremony, pairs well with Next's TS setup. Alternative: Jest — heavier config for ESM/TS in this setup, no added benefit here.
- **Prettier added alongside ESLint** — formatting consistency for a portfolio repo; configured to not conflict with ESLint's stylistic rules (ESLint stays focused on correctness).
- **Wrangler as a devDependency** — required to run Cloudflare Pages Functions locally (`wrangler pages dev`) and is free/local-only, no account needed for local dev.
- **Local dev workflow: `next build` (static export) + `wrangler pages dev ./out`** — the only way to exercise both the static frontend and the `/functions/api/recipe.ts` Pages Function together locally, matching production topology exactly. Alternative: a custom dev proxy/Express server — would diverge from the real Cloudflare runtime (different fetch/Request semantics), risking bugs that only show up in production.
- **Removed `cacheComponents`/`partialPrefetching` that `create-next-app` enabled by default** — Next.js 16's docs state Cache Components "requires the Node.js runtime," which directly conflicts with the locked `output: 'export'` (no server at all). Replaced with explicit `output: 'export'` + `images.unoptimized: true` per the locked architecture.
- **Separate `functions/tsconfig.json` for the Pages Function, excluded from the root tsconfig** — `@cloudflare/workers-types` globals (e.g. its `Response`/`Request`) would otherwise collide with the root config's `dom` lib used by the Next.js frontend. Keeping them in two separate TS programs avoids the clash entirely.
- **`next.config.ts` pins `turbopack.root` to the project directory via `fileURLToPath(import.meta.url)`** — a pre-existing, unrelated `package-lock.json` in the Windows user home directory was making Turbopack's root auto-detection walk up past the project folder, triggering a build warning. Pinning the root is the documented fix and keeps Turbopack from watching anything outside the project.
- **`npm audit` reports 5 high-severity issues in `braces` (via `eslint-config-next` → `@next/eslint-plugin-next` → `fast-glob`)** — dev-only lint tooling, not shipped to production, and the only fix (`npm audit fix --force`) downgrades `eslint-config-next` to `14.2.35`, incompatible with Next 16. Left as-is; revisit if a non-breaking patch lands upstream.
- **`@types/node` bumped from the scaffold's `^20` to `^22`** — matches the actually-installed local Node (v22.12.0) and was required anyway: Vitest 5's peer dependency needs `@types/node` ^22/^24.
- **Dev dependencies added**: `vitest` + `@vitest/coverage-v8` (unit tests for `/lib`, per Phase 1 requirement), `prettier` + `prettier-plugin-tailwindcss` (formatting, Tailwind class sorting), `wrangler` (local Pages Functions runtime), `@cloudflare/workers-types` (types for `PagesFunction`/`context` in `functions/api/recipe.ts`). All free, all dev-only.
- **Removed the scaffold's `next start` script** — meaningless under `output: 'export'` (no server to start); replaced with `pages:dev` (serves `/out` + `/functions` via Wrangler) and `preview` (build then serve), which is the real local-prod-parity workflow.
- **`vitest.config.ts` renamed to `vitest.config.mts`** — Vite's native config loader warned about ambiguous ESM-in-CJS-context for a plain `.ts` file with `import`/`export` syntax; `.mts` is unambiguous without touching `package.json`'s `type` field (which could have wider, unreviewed effects on the rest of the toolchain).
- **ESLint's first run on this project takes ~100s** (vs. near-instant on later runs) — the project lives inside an OneDrive-synced folder, which slows cold filesystem scans for `typescript-eslint`'s type-aware linting across ~400 `node_modules` packages. Confirmed it's not a real hang (exit 0, zero lint errors) by running with a generous timeout. Not fixing; just noting it so a "stuck" lint run isn't mistaken for a bug later.

## Phase 1 — Extraction engine

- **HTML scanning with regex, not HTMLRewriter** (`lib/extractPage.ts`) — we only need JSON-LD blocks plus a few `<meta>`/`<link>` tags. Plain string scanning is just as cheap on CPU, and it lives in framework-free `/lib`, so Vitest can unit-test it without the Workers runtime. Alternative: HTMLRewriter, which is streaming and Workers-native but only testable inside workerd.
- **Tolerant JSON parsing is strict-first** (`lib/parseJsonLoose.ts`) — `JSON.parse` is tried first. Only on failure does a single string-aware repair pass run (trailing commas, raw control characters in strings, invalid `\'` escapes, CDATA/comment wrappers), then a decode for fully entity-encoded blocks. Alternative: JSON5 or a similar dependency, rejected per the minimal-dependencies rule.
- **Breadth-first walk with an `@id` index, capped at 5000 nodes** — finds Recipe at the top level, in arrays, in `@graph`, or under `mainEntity`. It also resolves Yoast-style `{ "@id": … }` references for authors, images and steps, which WordPress sites rely on. The cap bounds CPU on pathological pages.
- **Pages with several recipes return all of them** (`{ ok: true, recipes: Recipe[] }`, shallowest first, empty stubs and exact duplicates skipped) — user asked for a picker. Phase 3 will show a picker with a one-line explanation when there is more than one; with exactly one, the UI goes straight to the overview. Superseded the earlier "first recipe only" choice.
- **Yield label must agree with the count** — `["8", "1 (9x5-inch) meatloaf"]` → `{ count: 8, label: "8 servings" }`, so scaling and label never contradict. Found during live testing on Allrecipes.
- **Float tidy-up (`2.0` → `2`) on yields and ingredients** — the Guardian's CMS serialises whole numbers as floats. Real decimals ("1.5", "1.50") are untouched.
- **Strip leading step numbering ("1.", "Step 2:") only when not followed by a digit** — so "1.5 kg potatoes…" and "1-2 minutes later…" aren't mangled.
- **SSRF guard** (`lib/validateUrl.ts`): http(s) only, ports 80/443 only, no credentials, no localhost/`.local`/`.internal`/single-label hosts, no private or reserved IPv4 ranges, and no IPv6 literals at all. Redirects are followed manually (max 5) so every hop is re-validated. Rejecting all IPv6 literals is simpler and safer than enumerating mapped/private v6 ranges, and recipe sites never use them. DNS-based rebinding isn't checked in code: Cloudflare's edge doesn't route Worker subrequests into private networks, and Workers can't resolve DNS themselves.
- **Honest User-Agent**: `CookMode/0.1 (+https://cookmode.pages.dev; …)`, with no browser impersonation. Sites that refuse it get a clean `BLOCKED` error with a link to the original. Bot-wall pages served with a 200 (Cloudflare "Just a moment", DataDome, PerimeterX) are recognised by markers and also reported as `BLOCKED` rather than `NO_RECIPE_FOUND`.
- **HTTP statuses for errors**: 400 `INVALID_URL`, 422 `NO_RECIPE_FOUND`, 504 `TIMEOUT`, 502 for the other upstream failures. The UI keys off `error.code`; statuses are for logs and devtools.
- **Caching**: success responses get `public, max-age=600`; errors get `no-store`, so a temporary block or timeout isn't cached. Every response also sends `X-Robots-Tag: noindex`.
- **Size cap enforced while streaming**, not only via `Content-Length` (which can be absent or wrong). The body is read chunk by chunk and the read is cancelled at 3 MB.
- **Timer detection returns the phrase's position** (`index`/`length`) so the cook-mode UI can turn the exact words into a tappable chip. Durations over 24h are ignored as "not a kitchen timer".
- **`scaleIngredient` also scales an equivalent measure immediately after the unit** ("200g/7oz", "1 cup (250ml)"). This goes slightly beyond "leading quantity only", because leaving "/7oz" unscaled next to a scaled "400g" would be wrong on screen. Pack sizes after a count ("1 x 400g tin", "1 (14-ounce) can") are still never scaled.
- **Scaled output uses unicode fraction glyphs** (½ ⅓ ¼ ¾ ⅔ ⅛) for cups/spoons/counts/imperial, even when the input used ASCII "1/2". They're more legible at distance. Metric g/ml are rounded: 1 dp under 10, whole numbers under 100, nearest 5 under 1000, nearest 10 above. kg/l keep up to 2 dp.
- **No new dependencies in Phase 1.**
- **Equivalent-measure scaling kept** ("200g/7oz" → "400g/14oz") — user deferred to judgement; long-term it avoids contradictory quantities on screen, and pack sizes are still protected.
- **Cook-time tidy-up of site data** (`lib/tidy.ts`) — strips per-ingredient prices, "(Note N)" pointers to notes we don't display, and recipe-plugin markup ("((…))", "(, sliced)"), and drops a condensed "Abbreviated Recipe"/"Summary"-style section when the full method is present (otherwise users would cook every step twice). Rules are deliberately narrow and covered by "leaves unchanged" tests. Alternatives: show raw text (noisy at the stove), or show notes (would require scraping non-structured content, out of scope).

## Pre-Phase 2 — UI standards

- **UI standards written down in `docs/UI-STANDARDS.md`** so Phase 2 tokens and Phase 3 screens are checked against one list (readability at distance, 56px targets, flat high-contrast, transform/opacity motion, platform-first). The user reviewed the list.
- **No component catalogue (21st.dev dropped at user's request); components hand-built on native elements.** Native `<dialog>` for the ingredients sheet, avoiding Radix and Vaul. APG spinbutton for servings. `scaleX` bar for timer progress, because an SVG ring animated with `stroke-dashoffset` would break the transform/opacity-only motion rule. Alternative: shadcn/21st components, which bring Radix/Vaul/motion dependencies and decorative styling.
- **Atkinson Hyperlegible Next shortlisted as a typeface**: built for low-vision legibility, OFL, and in `next/font/google`'s list in the installed Next.js (variable 200–800), so it needs no new dependency. Final choice happens at the Phase 2 checkpoint.

## Phase 2: Design system (proposal, awaiting approval)

- **`/styleguide` built from the real components** (`src/components/*`), so what gets approved is what Phase 3 ships, not a mock-up. It's `noindex` and its comparison fonts aren't preloaded, so it costs the app nothing.
- **Palette: warm off-white ground, near-black ink, one deep paprika accent** (`#8f2d0c` light / `#ff8a5c` dark). The accent was darkened from `#c2410c` because white on that was only 5.18:1, and the target is AAA. Every text pair is 7:1 or more in both themes. Alternatives: pure white/black (glare in a bright kitchen, harsher on OLED); a green accent (reads as "success", which we don't need); no accent (running timers would lose their unmissable state).
- **Palette as data in `lib/designTokens.ts`, plus a test that parses `globals.css`** to check the CSS matches and every text pair is AAA. Duplicated values can't silently drift, and a contrast regression fails CI.
- **`lib/contrast.ts`**: small WCAG 2 contrast helper, written instead of adding a colour library.
- **Five fluid type sizes** (display, title, step, body, small) using `clamp()` between 375px and 1280px; step text runs 30–44px; nothing below 16px.
- **Controls fully round, surfaces 20px radius, no lines or shadows**: surfaces are separated by tone. Hover moves one tone step (to `muted`/`line`), never via opacity, which would lower contrast.
- **Motion tokens as CSS variables** (press 100, quick 180, step 280, sheet 320ms; one easing family). Reduced motion zeroes `--motion-distance`, so the same keyframes become pure fades: one code path, no duplicate animations.
- **Recommended typeface: Atkinson Hyperlegible Next**, set as the provisional default in `layout.tsx` until approved. Note: its zero is slashed (0 vs O legibility); that's part of the design.
- **"Screen on" indicator uses an open-eye icon.** A phone-with-rays glyph read as a bin at 20px in testing.
- **Verification**: true 390px/360px phone emulation through the Chrome DevTools Protocol (a scratch script; nothing added to the project). It found and fixed a horizontal overflow in the step-screen preview. Interactions checked: the sheet traps focus and Escape returns focus to the trigger; stepper arrow keys rescale ingredients; step transition animates. Vercel's Web Interface Guidelines review added tap-highlight/`touch-action`, balanced headings, contrast-raising hovers and sheet overscroll containment. Its "Title Case" rule was deliberately not followed, because the standards specify sentence case.
- **Approved at the Phase 2 checkpoint (user)**: Font A (Atkinson Hyperlegible Next), palette neutrals, type scale, round corners, components and motion. Requested change: the accent.
- **Accent changed from paprika to enamel blue**: `#1d3fa3` deep cobalt (light) and `#8fbcf7` soft cornflower (dark), at the user's request for two blues that suit the warm neutrals. Cobalt on warm off-white echoes enamel kitchenware. All pairs stay AAA: white on cobalt 9.16:1, cobalt on ground 8.76:1 and on surface 7.94:1; ink on cornflower 9.91:1, cornflower on surface 8.70:1. Alternatives considered: `#1e40af` (7.56:1 on surface, too close to the limit), `#2a4bb0` (fails AAA on surface), and the brighter `#7cb4ff` for dark (more neon against warm black).

## Phase 3: Screens

- **One route; the URL is the state**: `/?url=…` (overview or picker), `&r=N` (recipe on a multi-recipe page), `&view=cook&step=N`, `&view=done`. Navigation uses the native History API, which this Next version keeps in sync with `useSearchParams`. Entering cook mode _pushes_ history, while steps and finishing _replace_ it, so the phone's back button leaves cook mode instead of walking back through every step. Alternatives: React state only (views not shareable, back button broken); separate routes (impossible to prerender per recipe under static export).
- **Pre-paint inline script picks the static fallback**: the prerendered HTML holds both the home screen and the loading skeleton. A one-line first-party script in `<head>` adds a class when `?url=` is present, so a shared link shows the skeleton from the first paint instead of flashing the home screen during hydration (measured locally at 1.6s+). Not a third-party script; nothing is fetched.
- **Home is a real `<form method="get" action="/">`**: it works before JavaScript loads. With JS, input is cleaned up by `lib/inputUrl.ts` (share text like "Try this! https://…", bare domains, trailing punctuation), and pasting a recognisable link submits immediately. "Paste from clipboard" only appears where `navigator.clipboard.readText` exists (detected with `useSyncExternalStore`, so there's no hydration mismatch).
- **Three "Or try one" examples** on home link to recipes verified in Phase 1, so a reviewer can try the app in one tap. They promote the creators; nothing is copied.
- **Timer engine in `lib/timer.ts`**: pure functions over end timestamps; `now` is injected, so it's fully unit-tested, including a nine-minute "backgrounded" gap. Timers are a list capped by `MAX_ACTIVE_TIMERS = 1`, so multiple timers later is a one-constant change plus UI.
- **Starting a second timer asks first ("Replace timer?") instead of silently replacing**: a stray tap on another chip must never kill the pasta timer. Alternative: silent replace (simpler, but loses a running timer).
- **Timers live at app level (`useTimers`)**, so a running timer survives leaving cook mode and stays visible on the overview.
- **Alarm**: three rising Web Audio beeps plus vibration, repeating every 2.5s for at most 12 rings or until dismissed. Audio is unlocked on the tap that starts the timer (browsers require a gesture). The finished state inverts the bar to ink with "Time's up", the strongest contrast on screen, and is announced through an assertive live region. Known limit: mobile browsers suspend timers and audio in background tabs, so the beep may wait until the tab is visible again. The time itself is always correct, because it's computed from the end timestamp.
- **Wake Lock**: requested on entering cook mode, re-requested on `visibilitychange` _and_ on the next `pointerdown` (some Safari versions need a gesture, per WebKit bug 255363), released on exit. "Screen on" only shows while a lock is actually held. Fails silently.
- **Keyboard**: ←/→ and PageUp/PageDown change steps, space toggles the step's timer (only when focus isn't on a control, so space still presses buttons), Escape exits. Each step change is announced as "Step 3 of 9. Section. Text.". Focus moves to each new screen's heading and into the step region in cook mode.
- **Swipe**: pointer events, 60px minimum and mostly horizontal (|dx| > 1.5·|dy|), `touch-action: pan-y` so vertical scrolling of long steps still works. Taps on buttons/chips are excluded. Big buttons remain the primary, accessible path.
- **`noindex` on recipe views is injected client-side** while `?url=` is present: static export can't vary headers by query string, and the single-Function rule rules out middleware. The home page stays indexable.
- **Images are hotlinked from the creator's CDN with `referrerPolicy="no-referrer"`** (privacy, and some CDNs reject foreign referrers), inside a fixed-ratio box with a typographic fallback, so a broken image never shifts the layout. The "View the original recipe" link deliberately keeps the default referrer policy, so creators can see the traffic Cook Mode sends them.
- **Attribution placement verified by measurement**: the credit link is fully visible and unobstructed without scrolling at 360×640, 390×844, 1280×800 and 1440×900. On desktop the sticky start button covers only the right column, and the image ratio widens to 16:9.
- **React hooks patterns** follow the strict `react-hooks` lint rules in eslint-config-next 16: adjust state during render on prop change (step direction), refs only in effects, per-render re-subscription for the keyboard listener, and `useSyncExternalStore` for browser capabilities.
- **New pure modules (unit-tested)**: `format` (times, clock, spoken clock), `timer`, `segmentStep` (step text → text/timer-chip runs), `inputUrl`, `yieldUnit` (stepper noun from the yield label: "cookies", "people").
- **Removed the scaffold's unused `public/*.svg`** (Next/Vercel logos from create-next-app).
- **Deferred to Phase 4**: the build warns that Next has no fallback-font metrics for Atkinson Hyperlegible Next, so no size-adjusted fallback is generated. Any resulting CLS will be measured and fixed there.
- **Verification**: a dependency-free CDP harness (scratch only, not in the repo) ran 31 end-to-end checks against the real Pages Function with live recipes (BBC Good Food, RecipeTin Eats, a two-recipe Guardian article, example.com for errors). It covered skeleton, noindex, titles, attribution visibility, scaling, cook-mode keys and swipe paths, timer start/pause/persistence, the sheet, finish, back-button behaviour, picker and error screens, with zero console errors. Visual passes at 390/820/1280px in light and dark, plus a forced clock jump to verify "Time's up" and the alert.

## Phase 4: Smoothness and polish (in progress)

- **Font self-hosted via `next/font/local`** (`src/fonts/AtkinsonHyperlegibleNext-Latin.woff2`, 34 KB variable, with `OFL.txt`) instead of `next/font/google`. `next/font/google` had no fallback metrics for this family (build warning), so no size-adjusted fallback was generated. The local file lets Next compute one (Arial at 99.36% size-adjust, matched ascent/descent), avoiding a layout shift on font swap.
- **`lib/displayFractions.ts`**: the typeface has ½ ¼ ¾ but no ⅓ ⅔ ⅛ ⅜ ⅝ ⅞ (verified by glyph-width tests in Chrome, even when requesting exactly those characters from Google Fonts). Ingredient lines therefore display those as "1 1/3" instead of falling back to a mismatched system glyph. Scaling logic is unchanged.
- **PWA**: `app/manifest.ts` (standalone, portrait, palette colours); icons drawn in code with `ImageResponse` (`src/lib/iconMark.tsx`: an original "C"/pan-rim arc plus a cornflower dot, inside the maskable safe zone) as the favicon, Apple icon and 192/512/maskable-512 PNGs via `force-static` route handlers; scaffold `favicon.ico` removed.
- **Service worker generated post-build** (`scripts/generate-sw.mjs`, `npm run build` runs it via `postbuild`): precaches only what `index.html` references plus manifest/icons; the cache name is a content hash, and old caches are deleted on activate. Navigation is network-first with an offline fallback to the cached shell. `/_next/static` is cache-first. `/api/*` and all cross-origin requests (recipe images) are never intercepted, so no recipe content is stored. Hand-written, no Workbox.
- **`public/_headers`**: CSP (`'self'` only for scripts, connections, fonts and workers, so no third-party script can run; images allow `https:` for creators' photos), Permissions-Policy, nosniff, Referrer-Policy, immutable caching for `/_next/static/*`, `no-cache` for `/sw.js`, and PNG content type for the extension-less icons. **Known local limitation**: `wrangler pages dev` skips `_headers` for static assets when a `functions/` directory exists (verified: the same `out/` served without `functions/` applies all rules). Re-check with `curl -I` after the first real deploy.
- **Verified**: 14/14 PWA/CSP checks (SW registers and controls; one versioned cache; no `/api` or third-party entries; offline home works; an offline recipe link shows "Can't reach Cook Mode"; CSP present with zero violations and the app hydrates under it on `/` and `/styleguide`).
- **Screens other than home load on demand** (`next/dynamic`), with the skeleton as their loading state. Overview and cook mode are preloaded as soon as a `?url=` is present, in parallel with the recipe fetch. Error copy moved to `errorCopy.ts` so titles don't pull in the error screen. The cook-mode screen is about 10 KB gz on top of the shared shell.
- **The pre-paint script starts the recipe request** (`window.__cookModeEarly`, consumed once by `recipeClient.ts`), so `/api/recipe` starts at about 0.1s instead of after hydration (about 1.4s in Lighthouse traces). On the overview, once the JSON arrives, it also preloads the recipe photo (the largest element on screen), with the same `no-referrer` policy so the `<img>` reuses it. Verified: one image request, started by the preload, with no hydration warnings. Alternative: wait for the JS (simpler, but the image request sat behind three sequential steps).
- **`prefetch={false}` on every `next/link`**: with one route, Next's prefetches (`?_rsc=` and `__next._tree.txt`) were pure overhead, three per example link on home.
- **Page title is a single React-managed `<title>`** (`PageTitle`, rendered in `page.tsx` outside the Suspense boundary so it's in the static HTML; CookModeApp sets it through a tiny store). The old `document.title` effect lost a race with Next's metadata `<title>` once recipe data started arriving before hydration finished: tabs showed "Cook Mode" on repeat visits. The root metadata no longer sets a title; the styleguide and 404 pages set their own. Alternative: React 19 `<title>` inside the Suspense content (not emitted into the static HTML from a fallback).
- **Buttons transition only `transform`** (no `background-color`), matching the transform/opacity motion rule; hover colour changes are now instant, as on the other controls.
- **Desktop overview's sticky start area** now has a solid background above and below the button, so ingredients no longer show through around it.
- **Skip link** ("Skip to content") in the layout, targeting `#main` on every screen, including the skeleton and cook mode.
- **Performance numbers are provisional until measured on the deployed site.** Local Lighthouse runs are unreliable on this laptop (CPU benchmark 264–1089 across runs, and Lighthouse warned about it). Five orphaned `wrangler pages dev` processes from the old `OneDrive\Desktop\CookMode` copy had been running since 17 Oct; they held ports 8788/8799 (so the first runs tested a stale build) and used about a core between them. They were stopped. Accessibility 100 and CLS 0 were stable on every run. Final Performance numbers will come from PageSpeed Insights after deployment.
- **Remaining Performance cost is mostly framework**: Next's router chunk and React hydration are the largest main-thread tasks. Further cuts would mean leaving `useSearchParams`/Suspense (a custom location store) or changing framework. Both conflict with locked decisions, so I didn't make either change.

## Phase 5: Ship prep

- **Final README** adds a feature list, commented-out screenshot placeholders, an ASCII architecture diagram, the "Why attribution is a design decision" section and a deploy settings table. Screenshots aren't committed: the useful ones show creators' recipe photos, which aren't ours to redistribute. The placeholder comment says to use a permitted or blurred photo.

- **`.node-version` pins Node 22** for Cloudflare Pages' build image, matching local Node 22.12 and `@types/node` ^22. Alternative: a `NODE_VERSION` environment variable in the dashboard, which works but lives outside the repo.
- **No `wrangler.toml`**: Pages' Git integration detects `functions/` automatically, and the build settings live in the dashboard (documented in the README). Fewer files, nothing to drift.

The npm 11.6 lockfile written on Windows was missing the top-level `@emnapi/core` and `@emnapi/runtime` entries (optional WebAssembly helpers for `sharp` and `@napi-rs/wasm-runtime`), so Cloudflare's `npm ci` refused to install. The diff only adds optional wasm entries and drops `"peer": true` metadata flags; no versions changed. `npm ci --dry-run` passes under both npm 10.9.2 and 11.6. Alternatives: pinning npm 11 in the build (another moving part) or adding `@emnapi/*` as direct dependencies (adds dependencies we don't use).

## After launch

- **Deployed as a Cloudflare Pages project, not a Worker.** The first attempt was created through the Workers flow, which ran `wrangler deploy`. Wrangler then auto-configured OpenNext (server-rendered Next.js), which conflicts with `output: 'export'` and wouldn't serve `functions/`. That project was replaced with a Pages project: framework preset None, `npm run build`, output `out`.
- **Live checks (2026-10-19)**: every `_headers` rule applies in production (CSP, Permissions-Policy, nosniff, immutable `/_next/static`, `no-cache` on `sw.js`, PNG content type for icons); the API sends `Cache-Control: public, max-age=600` and `X-Robots-Tag: noindex`. Live recipes worked from BBC Good Food, RecipeTin Eats, Serious Eats, Allrecipes, Budget Bytes, Sally's Baking Addiction and Bon Appétit. `example.com` returns `NO_RECIPE_FOUND`, `localhost` returns `INVALID_URL`, and a dead link returns `FETCH_FAILED`.
- **Official performance from PageSpeed Insights** (mobile): home 99, overview 97, cook 99; accessibility 100 and CLS 0 everywhere; TBT 10–60 ms. That confirms the low local scores came from the laptop's CPU. The table in the README replaces the provisional local numbers. Google's keyless PSI API hit its shared daily quota, so the web UI was used instead.
- **No focus ring on programmatic focus targets** (`[tabindex="-1"]:focus-visible`). The cook-mode step and each screen's heading take focus only so screen readers start there; they aren't controls. PSI's screenshot showed a fresh cook-mode link framing the whole step in a heavy black outline. Every interactive element keeps its 3px ring.
- **Committed smoke test** (`scripts/smoke.mjs`, `npm run smoke`): headless Chrome over the DevTools protocol checks every screen at 360/430/820/1440px for the right title, no horizontal overflow, no console errors, and key content (creator credit visible without scrolling). It came out of a retro: each phase had rebuilt a throwaway harness in scratch, and the title race was only caught by chance. Dependency-free (Node's built-in WebSocket and fetch, a local Chrome), so no Puppeteer or Playwright. It serves on a free port after checking nothing is listening there, and stops wrangler's whole process tree on exit, to avoid the stale-server problem. Mutation-tested: breaking the title update fails it with `title is "Cook Mode"`. Alternatives: Playwright (a large dependency plus browser downloads, against the minimal-dependencies rule) or keeping manual checks (they were lost every session).
